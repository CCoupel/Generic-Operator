Generic Operator

Un moteur d'opérateur Kubernetes générique, piloté par templates Jinja2 — avec Secure Namespace Operator comme implémentation de référence.

Installer Voir les releases Code source

Le problème

Construire un opérateur Kubernetes pour du provisioning à la demande — namespaces, quotas, isolation réseau, ingress, egress — demande une base solide (boucle de réconciliation, rendu de templates, suivi de révisions, RBAC) avant même d'écrire la première ligne de logique métier.

🔁

Code dupliqué à chaque nouveau besoin

La boucle kopf, le rendu de templates, l'application générique de ressources et le suivi de révisions se réécrivent identiques d'un opérateur à l'autre.

🕸️

Webhooks fragiles

Un webhook mutant/validant maison implique certificats TLS, cert-manager, disponibilité réseau vers l'API server — de la charge opérationnelle pour une logique souvent simple.

📦

Distribution artisanale

Sans registre OCI natif, publier et versionner un chart Helm pour une équipe plateforme reste manuel et peu reproductible.

Public visé : équipes plateforme / SRE qui opèrent du multi-tenant Kubernetes et doivent exposer du self-service namespace de façon sécurisée.

L'approche

Avant

  • Logique métier et mécanique d'opérateur mélangées dans le même code
  • Un webhook Flask + cert-manager pour la moindre mutation/validation
  • CRD, group, version codés en dur partout dans le code Python
→

Avec Generic Operator

  • Moteur générique (templates/core/) séparé de l'implémentation déclarative (templates/implementations/<nom>/)
  • Kyverno ClusterPolicy pour l'admission — zéro webhook à opérer
  • values.yaml::crdpilote le CRD ciblé — group/version/kind/plural jamais en dur

Secure Namespace Operator — l'implémentation de référence livrée

Provisioning de namespaces sécurisés avec isolation réseau Cilium, quotas de ressources, ingress multi-contrôleur (NGINX/HAProxy/Traefik) et gateway d'egress par VIP avec annonce L2 — le tout généré depuis des templates Jinja2, sans code Python spécifique par namespace.

Fonctionnalités

🧩

Moteur CRD-agnostique

kopf + rendu Jinja2 à délimiteurs personnalisés + application générique de ressources via DynamicClient.

🛡️

Isolation réseau Cilium

NetworkPolicies générées automatiquement, avec règles d'accès externe configurables (CIDR, FQDN, services, namespaces).

🌐

Ingress multi-contrôleur

NGINX, HAProxy ou Traefik au choix, un contrôleur dédié par namespace provisionné.

🚪

Egress VIP Gateway

Placement automatique de VIP avec annonce L2 et politiques Cilium — désormais unifié dans le moteur générique.

Installation

Depuis ghcr.io (recommandé)

helm install secure-namespace-operator \
  oci://ghcr.io/ccoupel/charts/secure-namespace-operator \
  --version 0.0.2 \
  --namespace namespace-operator \
  --create-namespace \
  -f values.yaml

Depuis les sources

git clone https://github.com/CCoupel/Generic-Operator.git
cd Generic-Operator
helm install secure-namespace-operator ./CHARTS \
  --namespace namespace-operator \
  --create-namespace \
  -f CHARTS/values.yaml

Configurer le CRD ciblé

Le moteur ne connaît aucun CRD en dur — tout passe par values.yaml::crd :

crd:
  group: secure-ns.example.com
  version: v1alpha1
  kind: SecureNamespace
  plural: securenamespaces

Prérequis, désinstallation et référence complète des champs du CRD : CHARTS/README.md · construire sa propre implémentation : HOWTO-NEW-IMPLEMENTATION.md
